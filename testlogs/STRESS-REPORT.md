## What the stress runs found

Seven defects, each one found by pushing the system until it gave way and then reading what broke rather than what was supposed to happen. All are fixed; the sections below are the numbers from the run after the fixes.

| # | Defect | Impact | Found by |
|---|---|---|---|
| 1 | Quadratic vector append (`np.vstack` per insert) | 403× slower inserts at 32k points; a scale run that never returned | ingest throughput decaying with corpus size |
| 2 | Index migration ran inline on the write path | one write blocked **30.8 s** while a graph was built under it | worst-case write latency at the strategy crossover |
| 3 | Catastrophic regex backtracking in the PII classifier | a single 1 MB ingest wedged the node for **79 minutes** at 100% CPU — a denial-of-service vector on an unauthenticated path | the adversarial phase hanging; `py-spy` stack dump |
| 4 | `slo.observe()` called only in the HTTP layer | the degradation ladder was blind to every query from the WebSocket, agent, mesh or internal retrieval: p99 **1,850 ms** against a 150 ms target with a burn rate of exactly 0.0 and nothing shed | sustained-overload ladder measurement |
| 5 | Semantic cache keyed on tenant only | a `collection="*"` answer was served verbatim for a scoped query — five hits from a collection holding nothing | chasing defect 7; scoped queries returning another scope's results |
| 6 | Inferred query narrowing applied as a hard filter | ordinary queries returned **zero** hits: `conveyor` → 5, `conveyor vibration night shift` → 0 on a corpus where every document contains all four words | manual probing after the cache fix stopped masking it |
| 7 | Tokenizer encoded the whole input to keep 128 tokens | 1 MB query 853 ms → 35.5 ms; the same text stored as a document paid it again on every rerank, making one adversarial query take 30 s | profiling the 1 MB query |
| 8 | In-flight sync outlived the storage handle | shutdown raised bare `RuntimeError` into un-awaited background tasks | never-retrieved future exceptions during soak |

Two of these — 3 and 6 — are the kind that do not show up in a demo. The first needs a hostile input nobody types by accident; the second looks like a working system returning an honest empty answer.

## Defects 1 and 2, measured before and after

The first pass never finished. Ingest throughput decayed as the corpus grew — 75 docs/s at 2k points, 53 docs/s at 10k — and a scale phase at 32k points ran for 25 minutes without returning. Two causes, both real:

**1. Vector append was quadratic.** `np.vstack([matrix, row])` allocates a new array and copies every existing row, so building an index one point at a time cost O(n) per insert and O(n²) overall. Three separate hot paths did it.

| Corpus | Before µs/insert | After µs/insert | Speed-up | After inserts/s |
|---|---|---|---|---|
| 2,000 | 109.6 | 7.6 | **14×** | 131,277 |
| 8,000 | 587.3 | 8.4 | **70×** | 119,260 |
| 32,000 | 3,367.6 | 8.3 | **403×** | 119,797 |

Per-insert cost grew **30.71×** over a 16× corpus before the fix (quadratic), and **1.1×** after (flat). The fix is a growable buffer with geometric capacity that exposes its filled region as a *view*, so every existing `matrix @ query` stays one BLAS call over contiguous memory.

**2. Index migration ran on the write path.** When a collection crossed the flat→HNSW crossover, the rebuild happened inline, inside the write that happened to cross it.

| Measurement | Before | After |
|---|---|---|
| Worst single write | **30,770 ms** | **2.7 ms** |
| Where the rebuild runs | inline, blocking ingest | maintenance lane (68s, shed under pressure) |
| Writes stalled behind it | all of them | none |

One unlucky write blocked for **30.8 seconds** while a graph was built underneath it. The decision is still made on the write path; the work is not.

Peak **29,421 embeddings/s** at batch 128 — about **29 per millisecond** on four cores with no GPU. Throughput *falls* above batch 128: the working set stops fitting cache, so bigger batches buy nothing. The tokenizer sustains 1,255,229 tokens/s.

> On "billions per millisecond": that would be ~10¹² ops/s, several orders of magnitude past this machine's memory bandwidth. The honest ceiling is 29/ms on this box, and the table above says where it flattens and why.

## 3. Corpus scale

| Points | Strategy | Recall@10 | Search p50 | Search p95 | Corpus ingest | RSS |
|---|---|---|---|---|---|---|
| 1,000 | flat | 1.000 | 0.178 ms | 0.281 ms | 14 s (72/s) | 727 MB |
| 5,000 | flat | 1.000 | 0.278 ms | 0.857 ms | 81 s (62/s) | 933 MB |
| 20,000 | flat | 1.000 | 1.326 ms | 1.796 ms | 467 s (43/s) | 1553 MB |

The last column but one is the *whole ingest path* for that corpus — embed, WAL, classify, extract facts, index — not index construction, which it dwarfs. It is the encoder's cost, and it is the same quantity section 2 measures.

**The index stayed exact at every scale tested, and that is the cost model working rather than failing to fire.** Recall is 1.000 because the search is exhaustive, and p95 at 20,000 points is 1.796 ms — one BLAS call over a 20,000 x 256 matrix. The device-calibrated crossover sits far above this because a graph traversal in the Python interpreter loses to contiguous SIMD arithmetic until the corpus is very large; an adaptive index that switched here would be trading exact results for a slower approximate one.
